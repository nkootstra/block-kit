---
title: Fallback canary
description: How this renderer falls back for a block type it doesn't recognize, and the synthetic block used to test that path.
---

Slack Block Kit has a fallback convention: when a client doesn't recognize a block's `type`, it can render
that block's producer-supplied `fallback` array in its place instead of dropping the content. `fallback_canary`
is a synthetic block type this library ships to exercise that path in tests and demos. It isn't a block Slack
itself sends. Point any real, unrecognized block at a `fallback` array and this renderer handles it the same way.

<Preview
  payload={{
    blocks: [
      {
        type: "fallback_canary",
        fallback: [
          {
            type: "header",
            text: { type: "plain_text", text: "Fallback demo" },
          },
          {
            type: "section",
            text: {
              type: "mrkdwn",
              text: "Your client does not recognize this block, so it is showing the producer-supplied *fallback* instead of dropping the content.",
            },
          },
          {
            type: "context",
            elements: [{ type: "mrkdwn", text: "Rendered via the fallback convention" }],
          },
        ],
      },
    ],
  }}
/>

## Fields

<TypeTable
  type={{
    type: {
      type: "string",
      description: "Always `fallback_canary`.",
      required: true,
    },
    fallback: {
      type: "Block[]",
      description:
        "Blocks to render in place of this one. Slack renders the whole list inside the single wrapper it gave the unknown block, which is a flex row, so the fallback blocks sit side by side rather than stacking vertically.",
      required: true,
    },
  }}
/>

This isn't a standard Block Kit block type. It's a test fixture for the fallback mechanism itself. When this
library encounters a block `type` it doesn't have a component for, it looks for a `fallback` array on that
block and renders those blocks instead of showing nothing.
